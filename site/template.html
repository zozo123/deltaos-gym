Six Linux coding tasks

Each task asks you to change one piece of code. The checks show whether your change works and which cases it covers.

  1. Allow one new connection. Let one user connect to a specific address and port over TCP. Keep every other allow or deny decision the same.
  2. Enforce a quota. Reject a charge if it exceeds the remaining budget or would make the total wrap around. A rejected charge must leave both counters unchanged.
  3. Detect a kernel bug. Flag exactly the input values that cause an 8-bit calculation to overflow in Linux’s IPv6 routing code.
  4. Replace a file safely. If the machine crashes during an update, readers must find either the complete old file or the complete new one.
  5. Start a worker with the right file. Pass the worker only the file handle it is authorized to inherit. Wait for it to finish and report failure if it fails.
  6. Diagnose a failing service. Choose the cheapest set of measurements that can tell every possible cause apart within the given limits.

Each result lists what was tested on Linux and what was proved under a model. The sections below show how earlier checks missed bugs and how the current checks catch them.

How the first graders were fooled

None of these needed a clever attack. Most are a few lines of C.

1. It tests one program and ships another

The egress task asks for a decision function that lives inside a cgroup/connect4 BPF program. The v0.5 grader built the function for x86, ran 26,536 cases against it, then checked that the same file also compiles for BPF.

The obvious fix is to preprocess the candidate for the BPF target once and test, prove and compile that one text. It is not enough. sizeof(long double) is 16 on x86-64 and 8 for BPF, so if (sizeof(long double) == 8) return 1; is still two programs, and so is code that compares the address of a local variable with 0xff00…, where kernel stacks live. So the source must now be plain integer C, the part of C on which the two targets agree: no sizeof, no floating point, no addresses, no asm, no builtins. With the kernel tier on, the compiled bytecode also answers every test case inside the kernel.

2. It lets the candidate into its own process

Four of the five graders loaded the candidate with ctypes or let the process hosting it print the verdict.

Candidate code now runs only in a sandbox process. In a verifier container the grader is root and the candidate is another user: it cannot write the verdict directory, cannot read tests/, and everything it started is killed before the verdict is written. Graders compare raw answers with the contract themselves, so there is nothing to print.

3. It samples where it could prove

v0.5's sampler hits that input with probability about 2-88 per case. A bounded model checker does not guess. CBMC proves the function equal to the contract for all 2113 inputs, or hands back the input where they differ:

"counterexample": {
  "reason": "counterexample_from_model_checker",
  "witness": {"uid": 3237998146, "ip": 134744072, "port": 31337, "proto": 6, "prior": 0},
  "expected": 0
}

3237998146 is 0xC0FFEE42. The proof for the reference takes [[CBMC_SECONDS]] seconds.

4. Its model of the OS is kinder than the OS

The crash-safety task checks publish() against a model of write, fsync, rename and directory fsync. The v0.5 model let you repair a failed fsync by calling it again.

The same model accepted fsync on a closed descriptor, injected EINTR once and only before the first byte, and injected one fault per run. The new model states its rules in the task's header, and the grader explores every schedule of short writes, interruptions and up to two I/O errors for small payloads: [[VFS_SCHEDULES]] schedules for the reference, each checked at every crash point.

5. It never asks the question it states

The descriptor task says: return non-zero when the worker fails, survive a signal during waitpid, pass exactly the authorized descriptor. The v0.5 grader never ran a failing worker and never sent a signal. Its test layout happened to put the right file at descriptor 3 in every case, so a launcher that never looked at its authorized_fd argument passed.

Five such launchers got full reward. Each requirement now has a case that fails without it, and each task has controls for the other direction too: correct solutions written differently from the reference, which must be accepted. [[V05_FALSE_REJECT]]

What a pass means now

The reward is still one bit. Next to it the grader writes a receipt that says what the bit rests on, claim by claim. This is the reference solution of the egress task, graded with the kernel tier on:

    [[LADDER]]

No class implies another. The kernel verifier accepting a program says it is safe to run, not that it is right. A proof is a statement about CBMC's semantics of C, not about a compiler. The receipt also carries the artifact's SHA-256, the seed that replays the episode's hidden cases, a digest of the grader, and how the candidate was isolated. Evidence classes, what the graders defend against.

The graders are public. Nothing depends on a secret test set: hidden cases are drawn fresh for every episode, and the strongest tiers do not sample at all.

Where this fits: shirudo

shirudo is a new open-source eBPF security platform. A Linux machine runs only the BPF its operator signed, every load is measured into the TPM, and fixes ship as signed micropatches called upatches. Its front page lists agents among the people who will write them.

Its documentation is exact about where its guarantee ends. Of the signature it says: “it shows who built the upatch, not that the upatch is correct.” The kernel verifier does not close that gap. A program that drops every packet is perfectly safe.

One task here is taken from shirudo's own tutorial, which turns the fix for an 8-bit overflow in the IPv6 RPL routing code (CVE-2026-63984) into a detector. The agent writes the detector's predicate. The grader runs all 256 argument values natively, proves the same statement with CBMC, loads the fentry program on a real kernel, and evaluates the compiled predicate for all 256 values inside the kernel through a SEC("syscall") test run, the program type shirudo itself uses for upatch self-tests.

It does not send the packet that triggers the bug. On an unfixed kernel that would corrupt memory, so the evidence for the dangerous branch is enumeration and proof, and the receipt says the hook was attached but not driven. Some properties of a mitigation cannot be tested on the system it protects.

scripts/receipt_gate.py is the small piece that goes in front of a signing key: it exits 0 only if a receipt matches the SHA-256 of the file you are about to sign and carries the evidence classes you require. The gym is independent of shirudo and not affiliated with it. More, including what is only a proposal.

Run it

git clone https://github.com/zozo123/deltaos-gym && cd deltaos-gym
docker build -t deltaos-dev -f qa/Dockerfile.dev qa

# grade the reference, the starter, and every control of one task
docker run --rm -v "$PWD":/gym -w /gym deltaos-dev \
    python3 scripts/run_controls.py egress-policy-delta

# everything, 5 fresh seeds each; add --privileged and --kernel for the kernel tier
docker run --rm -v "$PWD":/gym -w /gym deltaos-dev python3 scripts/release_qa.py

# as Harbor tasks
harbor run -p tasks/vfs-crash-atomicity -a oracle

The graders compile and execute what they are given. Run candidates you did not write only in a container or VM you can throw away, and turn the kernel tier on only there.

Limits

  • Six tasks is a seed, not a benchmark. The graders, their controls and the write-up of how they failed are the contribution.
  • The crash model is small and stated. It is not ext4.
  • Proofs are within CBMC's semantics of C. Compilers and hardware are outside them.
  • Without root there is no second user to run the candidate as. Local runs say so in the receipt.
  • Receipts are unsigned.
  • Nothing here has run on shirudo's own toolchain. The upatch task loads through libbpf on a stock kernel.
